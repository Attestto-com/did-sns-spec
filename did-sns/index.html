1. Abstract

The did:sns method binds W3C Decentralized Identifiers to Solana Name Service (SNS) domains. Unlike account-anchored methods (e.g., did:sol), did:sns is name-anchored — the identity persists across key rotations, wallet migrations, and custodial changes.

This specification is parent-agnostic: it works equally whether the root domain is attestto.sol (platform-operated) or crbank.sol (tenant-operated). Any SNS domain owner can anchor DIDs under their namespace.

Key properties:

  • Name-portable — identity persists across key rotations and wallet migrations
  • Hierarchical control — subdomains inherit controller relationships from parent domains
  • Human-readable — DIDs map to memorable SNS names (e.g., did:sns:alice.attestto)
  • On-chain verifiable — all resolution data is anchored to Solana with sub-second finality
  • Issuer-signed proofs — SAS attestations provide cryptographically verifiable claims, not self-asserted data

2. Architectural Rationale: The Living DID

Most blockchain-based DID methods couple where data is found with how data is proved into a single account. This forces a trade-off: either the system is too simple (self-asserted, no issuer trust) or too complex (every claim update requires credential reissuance).

The did:sns method separates these concerns:

LayerRoleAnalogy
SNS Domain (.sol)Public lookup registry — where you find the identityThe name on a bank folder
SNS Data Buffer (bytes 96+)High-speed pointer to the proofA sticker: “See Official Audit #88”
SAS Attestation (on-chain)Issuer-signed, verifiable proof of claimsThe stamped, notarized documents inside
The “Living DID”: Traditional DIDs are static — if a user’s KYC level changes, the entire credential must be reissued. With SAS as the proof layer, only the attestation updates. The .sol domain stays the same, but what it proves stays current in real-time.

3. DID Syntax

The method name is sns. A DID using this method MUST begin with did:sns:. Per DID Core, the method name MUST be lowercase.

3.1 ABNF Grammar

did-sns       = "did:sns:" [ network ":" ] sns-name
network       = "mainnet" / "devnet" / "testnet"
sns-name      = label *( "." label )
label         = 1*( ALPHA / DIGIT / "-" )

When the network component is omitted, mainnet is assumed. The .sol suffix is optional — the resolver strips it before lookup.

3.2 Examples

DIDDomainNetworkType
did:sns:attesttoattestto.solmainnetPlatform root
did:sns:alice.attesttoalice.attestto.solmainnetPlatform subdomain
did:sns:crbankcrbank.solmainnetTenant root
did:sns:alice.crbankalice.crbank.solmainnetTenant client
did:sns:devnet:alice.attesttoalice.attestto.soldevnetDevnet qualifier

3.3 Hierarchy Constraint

Max 2 levels: SNS supports a parent domain and one subdomain level. Three-level names (e.g., dept.company.attestto) are not supported.
StrategyStructureUse Case
Tenant Root Domain (recommended)alice.crbank.solTenant owns root domain; cleanest hierarchy
Flat Namespacingcrbank-alice.attestto.solAll under platform domain; hyphen-separated tenant prefix

3.4 Trust Hierarchy

The naming convention encodes an explicit trust chain:

Model A — Tenant Root Domain (Recommended for Institutions): attestto.sol → Platform Authority crbank.sol → Tenant Authority (self-sovereign) ├── alice.crbank.sol → End user (controller: did:sns:crbank) └── bob.crbank.sol → End user (controller: did:sns:crbank) Model B — Platform Root with Flat Namespacing: attestto.sol → Platform Authority ├── crbank-alice.attestto.sol → Tenant client (controller: did:sns:attestto) └── alice.attestto.sol → Direct platform user

Cross-Domain Trust: When a tenant uses their own root domain (crbank.sol), the platform root is NOT the controller. Trust between independent roots is established via alsoKnownAs references and LEI bridge attestations, not the controller hierarchy.

5. CRUD Operations

5.1 Create

A did:sns DID is created by registering an SNS domain on Solana. The DID exists implicitly once the NameRegistry account is created on-chain.

StepActionOn-Chain Effect
1Register SNS domain (Bonfida SDK / SNS CLI)NameRegistry created; owner = registrant’s Solana key
2Write DID metadata to data buffer (optional)Magic 0x44494401 + flags + keys at offset 96
3Create subdomain (optional)Child NameRegistry with parent PDA as seed
4Link SAS attestation (optional)SAS UID written to buffer; HAS_SAS flag set
No DID registration transaction required. Any SNS domain automatically has a resolvable DID. The resolver constructs a minimal DID Document from the owner key even without explicit metadata.

5.2 Read (Resolve)

Resolution fetches the NameRegistry account from Solana and constructs a W3C DID Document.

Algorithm

resolve(did): 1. Parse DID → extract sns-name and optional network 2. Strip ".sol" suffix if present 3. Validate hierarchy depth (max 2 levels) 4. Hash domain: SHA-256("SPL Name Service" + name) 5. Derive PDA: FindProgramAddress([hash, TLD_PARENT], SNS_PROGRAM) • For subdomains: derive parent PDA first, then child with \0 prefix 6. Fetch AccountInfo from Solana RPC 7. If not found → return notFound error 8. Extract owner key (bytes 32-63) 9. If owner is zero address → return deactivated 10. Check data buffer (bytes 96+) for magic 0x44494401: a. Found → parse DID metadata (v1 or v2 schema) b. Not found → minimal fallback (owner key only) 11. If v2 + HAS_SAS flag → follow SAS UID for issuer-signed claims 12. Set controller from parent domain hierarchy 13. Populate service endpoints 14. Return DidResolutionResult

Figure 2 — Resolution pipeline

Resolution Priority

  1. Check data buffer for 0x44494401 magic → parse DID metadata (v1 or v2)
  2. If v2 + HAS_SAS → follow SAS attestation UID for issuer-signed claims
  3. Fallback → minimal DID Document from owner key only

Error Codes

CodeHTTPCondition
invalidDid400Malformed syntax, wrong prefix, invalid characters
notFound404SNS domain not registered or account does not exist
deactivated200Owner is zero address; didDocumentMetadata.deactivated = true
internalError500RPC failure or resolver error

5.3 Update

DID Documents are derived from on-chain state, not stored as-is. Updates happen at the Solana layer:

Update ActionOn-Chain OperationDID Document Effect
Rotate keysTransfer SNS domain to new owner#solana-key changes to new owner’s key
Update metadataWrite to data buffer (offset 96+)Flags, ECIES key, SAS UID updated
Link SAS attestationSet HAS_SAS flag + write UIDIssuer-signed claims in resolution metadata
Transfer subdomainReassign subdomain ownerNew key in verification methods
Name portability: When domain ownership transfers, the DID identifier remains stable. Only the verification methods change. This is a key advantage over account-anchored methods.

5.4 Deactivate

A DID is deactivated by transferring ownership to the system program (all-zero address):

{
  "@context": "https://w3id.org/did-resolution/v1",
  "didDocument": null,
  "didResolutionMetadata": { "contentType": "application/did+ld+json" },
  "didDocumentMetadata": { "deactivated": true }
}

6. On-Chain Metadata Schema

DID metadata is stored in the SNS account data buffer (bytes 96+), identified by magic bytes 0x44494401.

SNS NameRegistry Account: +--------------------------------------------------+ | HEADER (96 bytes -- fixed by SNS program) | | +-- Parent Key (bytes 0-31) 32 bytes | | +-- Owner Key (bytes 32-63) 32 bytes | | +-- Class Key (bytes 64-95) 32 bytes | +--------------------------------------------------+ | DATA BUFFER (bytes 96+ -- DID metadata) | | +-- Magic + Version + Flags + SAS UID | | + ECIES key + Vault hash + Doc hash | +--------------------------------------------------+

v2 Schema Layout (160 bytes)

FieldOffsetSizeDescription
Magic040x44494401 (“DID\x01”)
Version41Schema version (0x02 for SAS-linked)
Flags51Bitfield (see below)
SAS UID632SAS attestation PDA address
ECIES Key3833Compressed secp256k1 public key for encryption
Vault Hash7132SHA-256 of vault service endpoint URL
Doc Hash10332SHA-256 of canonical DID Document
Reserved13525Zero-filled (future use)

Flags Bitfield

BitFlagMeaning
0x01ACTIVEDomain is active
0x02HAS_SBTSoul-Bound Token minted
0x04IS_TIER3Self-Sovereign ID tier
0x08HAS_LEILEI/vLEI credential linked
0x10HAS_SASSAS attestation linked (proof layer)

7. SAS Integration (Proof Layer)

The Solana Attestation Service (SAS) provides the issuer-signed proof layer. The SNS data buffer points to a SAS attestation; the resolver follows the pointer to fetch verifiable claims.

SNS Data Buffer SAS Attestation (on-chain) +-------------------------+ follows UID +-----------------------------+ | Magic + Version | -----------> | credential: Issuer PDA | | Flags (HAS_SAS = 0x10) | | schema: DID Identity v1 | | SAS Attestation UID ----| | signer: Authorized key | | ECIES Public Key | | data: | | Vault Endpoint Hash | | lei_hash (SHA-256) | +-------------------------+ | role_level (1-4) | ^ owned by | jurisdiction (ISO 3166) | Domain owner | zkp_proof_hash | (or platform) | expires_at | | tokenAccount (SBT) | +-----------------------------+ ^ signed by Authorized Issuer

SAS Hierarchy

Credential (Issuer Authority) +-- Schema (DID Identity Attestation v1) +-- Attestation (per-user, per-domain) |-- data: Borsh-serialized identity claims |-- expiry: Unix timestamp |-- signer: Authorized signer key +-- tokenAccount: Optional Token-2022 SBT

8. Security Considerations

  • No PII on-chain. All personal data is in encrypted Data Vaults. On-chain stores only cryptographic keys, flags, and hashes.
  • Class Key lock. Platform-issued subdomains use nameClass = Platform Authority for cryptographic proof of issuance. Only the class key holder can create or transfer class-locked subdomains.
  • Bidirectional linking. SNS→SAS (via HAS_SAS flag + UID) and SAS→SNS (via did_reference field) prevents attestation spoofing.
  • Deactivation detection. Zero-owner check returns deactivated: true.
  • RPC trust model. The resolver trusts the Solana RPC. For high-assurance use cases, verify against multiple providers or a local validator.
  • Key compromise. Transfer the domain to a new key immediately. The DID identifier remains stable; only verification methods change.
  • Cryptographic separation. Because SAS manages the proof state, even if someone compromises the SNS domain, they cannot forge the issuer-signed attestation.
  • Subdomain isolation. Each subdomain is a separate on-chain account. Compromising one subdomain does not affect siblings or the parent domain.

9. Privacy Considerations

  • Selective disclosure. SD-JWT (RFC 9449) enables per-field disclosure with individual salt and hash per attribute.
  • ZKP predicates. BBS+ signatures for unlinkable proofs (e.g., age ≥ 18, country membership) without revealing the underlying value.
  • Consent-gated access. 2-of-2 Shamir key-splitting for high-assurance credentials. Neither the platform nor the user alone can decrypt proof data.
  • Correlation risk. SNS names are public. Users requiring unlinkability should use fresh subdomains per relationship or ZKP-based presentations.
  • GDPR / Law 8968 compatibility. Right to erasure is satisfied by deleting vault content and deactivating the DID. On-chain pointers become meaningless without the encrypted payload. Dual-key encryption ensures data is pseudonymized beyond any single custodian’s control.
  • On-chain minimization. The NameRegistry stores only cryptographic keys, flags, and hashes — never names, emails, or personal data.
  • LEI privacy. LEI numbers in SAS attestations are stored as SHA-256 hashes. Verifiers hash a known LEI to compare, without the on-chain data revealing the LEI itself.

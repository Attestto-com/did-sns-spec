Overview

The did:sns method binds W3C Decentralized Identifiers to human-readable Solana Name Service (SNS) domains. Unlike account-anchored methods, did:sns provides name-portable, hierarchically-controlled identities suitable for institutional and consumer use cases.

1. DID Syntax

The did:sns identifier follows the W3C DID Syntax (§3.1):

did:sns:[network:]<name>.sol

Examples

did:sns:attestto.sol                  # Platform root domain
did:sns:alice.attestto.sol            # Subdomain (platform-issued)
did:sns:crbank.sol                    # Tenant root domain
did:sns:alice.crbank.sol              # Tenant client subdomain
did:sns:crbank-alice.attestto.sol     # Flat-namespaced tenant client
did:sns:devnet:alice.attestto.sol     # Devnet network qualifier

ABNF Grammar

did-sns         = "did:sns:" [ network ":" ] sns-name
network         = "mainnet-beta" / "devnet" / "testnet"
sns-name        = label *( "." label ) ".sol"
label           = 1*( ALPHA / DIGIT / "-" )

When the network component is omitted, mainnet-beta is assumed.

2. Resolution Algorithm

  1. Parse the DID identifier. Validate syntax against the ABNF grammar.
  2. Derive the Solana PDA via the SPL Name Service program (namesLPneVptA9Z5rqUDD9tMTWEJwofgaYwp8cawRkX). For subdomains, derive parent PDA first, then child PDA with parent as seed.
  3. Fetch the account via Solana RPC. Read the NameRegistry header: parent key (32 bytes), owner key (32 bytes), class key (32 bytes).
  4. Check deactivation: if owner is the system program (all zeros), return deactivated: true in document metadata.
  5. Read metadata from the data buffer. Check for magic bytes 0x44494401 at offset 96. Parse v1 or v2 schema.
  6. Follow SAS: if the HAS_SAS flag (0x10) is set and a SAS attestation UID is present (v2), fetch the attestation from the Solana Attestation Service for enrichment.
  7. Construct the DID Document with verification methods, service endpoints, controller hierarchy, and optional LEI/vLEI enrichment.

4. On-Chain Metadata Schema

DID metadata is stored in the SNS account data buffer, following the NameRegistry header (96 bytes). The schema is identified by magic bytes 0x44494401 ("DID\x01").

v2 Layout (current, 135 bytes)

OffsetSizeField
04Magic bytes (0x44494401)
41Schema version (2)
51Flags (ACTIVE, HAS_SBT, IS_TIER3, HAS_LEI, HAS_SAS)
632SAS attestation UID
3833ECIES public key (compressed secp256k1)
7132Vault endpoint hash (SHA-256)
10332DID Document hash (SHA-256)

5. DID Lifecycle: Issue Once, Evolve Forever

A did:sns identifier is created once and never re-issued. The DID persists across key rotations, wallet migrations, KYC upgrades, and custodial changes. Only permanent deactivation ends a DID’s life.

EventDID IdentifierWhat Changes
Key rotation (wallet transfer)Unchanged#solana-key verification method
KYC/LEI credential updateUnchangedNew SAS attestation PDA
Tier upgrade (1 → 2 → 3)UnchangedFlags, new verification methods
Encryption key rotationUnchangedECIES public key in buffer
Suspension / recoveryUnchangedActive flag cleared / restored
Organizational transferNew DIDNew domain = new DID (linked via alsoKnownAs)
DeactivationFrozendeactivated: true; resolvable for audit only

The DID identifier is a name, not a key. Names persist; keys rotate. See §8.3 of the full spec for the detailed lifecycle phases and comparison with other DID lifecycle models.

Root Domains as Organizational DIDs

Root domains (crbank.sol) are first-class DIDs representing organizations. Subdomains represent individuals under that org. The controller field establishes the trust hierarchy:

LevelExampleRepresents
Platform rootdid:sns:attestto.solTrust anchor
Tenant orgdid:sns:crbank.solBank (KYB/vLEI verified)
Individualdid:sns:alice.crbank.solClient/employee (KYC verified)

Org domains can change owners (acquisition, merger, rebrand, regulatory seizure). Client DIDs survive — only the namespace controller changes. Vault data is protected by 2-of-2 Shamir (acquiring entity gets the “phonebook” but not the “safe”). See §5.6 of the full spec.

6. Security Considerations

  • No PII on-chain. All personal data is stored in encrypted Data Vaults. On-chain stores only an identity_hash (SHA-256 commitment).
  • Class Key lock. Platform-issued subdomains are created with nameClass = Platform Authority, providing cryptographic proof of issuance.
  • Bidirectional linking. SNS→SAS (via HAS_SAS flag + attestation UID) and SAS→SNS (via did_reference field) prevents attestation spoofing.
  • Deactivation detection. Zero-owner check returns deactivated: true in document metadata.
  • Stateless resolution — no DID Log. Unlike log-based methods (did:webvh), did:sns uses a fixed 192-byte mutable buffer. Resolution is O(1) regardless of identity age. No accumulated signatures, no log replay. This makes did:sns structurally immune to post-quantum log bloat (PQ signatures are 2–17 KB each; a 5-year DID log could reach 1–4 MB). See §8.3 of the full spec.
  • Full audit trail via Solana transaction history. Every buffer mutation is a signed, validator-attested transaction. Auditors can filter by signer (previous owner, platform authority) and reconstruct the complete chronological history without a DID Log. See §8.3 of the full spec.
  • Post-quantum readiness. HAS_PQ flag reserved. PQ keys (ML-DSA-44, ML-KEM-768) stored in SAS attestation layer, referenced by hash in the fixed-size buffer. Hybrid mode (classical + PQ) defined for the transition period. See §8.1 of the full spec.

7. Privacy Considerations

  • Selective disclosure. SD-JWT (RFC 9449) enables per-field disclosure with salted hashes.
  • ZKP predicates. BBS+ signatures for unlinkable proofs (age verification, country membership).
  • Consent-gated access. 2-of-2 Shamir key-splitting for Tier 3 credentials.
  • GDPR compatibility. Right to erasure satisfied by deleting vault content (on-chain pointer becomes meaningless).
